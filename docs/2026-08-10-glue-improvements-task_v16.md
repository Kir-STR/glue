**Модель публикации (С4, § 7) и version-инварианты (сквозные, два раздельных — цикла нет):**

**Continuous release:** marketplace-entry указывает на `./plugins/glue` текущей ветки — поэтому **merge в main любого изменения `plugins/glue/**` (с обязательным бампом) и есть публикация новой версии**; тег — постфактум-фиксация, не гейт публикации. **Merge-гейт и release-гейт не объединяются** (`operator-gate.md`: outward publication и merge требуют отдельных подтверждений): plugin-changing PR проходит **два независимых подтверждения перед одним физическим merge** — (1) буквальное подтверждение публикации версии X.Y.Z; (2) после свежей перепроверки — отдельное «мержь». Строка «merge = публикация версии X.Y.Z» в PR-описании раскрывает эффект, но не заменяет авторизацию. Триггер перехода на controlled release — см. С4, исполняется пунктом 6.3.

- **Pre-merge (CI, вводится в W2):** если diff `plugins/glue/**` между PR-веткой и base непуст → `version` в `plugin.json` обязан отличаться от version на base; **и тег `glue-v<новая version>` ещё не должен существовать**. Сравнение с base — работает до появления какого-либо тега вообще.
- **Post-merge / release-фиксация (вводится в W3 вместе с первым тегом):** тег `glue-v<version>` указывает на merge-коммит, опубликовавший эту версию, и содержимое `plugins/glue/**` на теге соответствует ей; проверка исполняется при создании тега.
- **Создание тега — operator-действие фиксации** (какие опубликованные версии закрепляются тегами и Release-нотами), но не механизм контроля публикации: публикацию контролирует merge-гейт.

Rationale: version — cache key и сигнал обновления в модели Claude Code; изменённые биты под старой версией дают новым установкам другой код под тем же номером. До введения CI-проверок инварианты действуют как правила PR-ревью.

### 3.1 Frontmatter-схема карточек (W1, EN) — контракт задан, не изобретается исполнителем

```yaml

type: decision                 # согласовать с типами из 3.0
status: active                 # active | superseded | retired
supersedes: dec-2026-012
valid_from: 2026-03-14
source:
  path: docs/2026-08-10-glue-improvements-task_v16.md
  sha: <commit SHA файла-источника>        # обязателен для kind: repo-doc
  section: "7. Принятые решения"           # точный текст заголовка (exact match)
  kind: repo-doc                           # repo-doc | spec | external
  read_at: 2026-08-10
confidence: stated             # stated | inferred | assumed
links: [dec-2026-001]          # плоский список датированных ID — ровно область 5.1

Принятые решения».

### С1 (принято). Трейсер 5.2 — первым в W4.

Условия, входящие в решение:
1. Подсрез 1 трейсера (provider-контракты + schema трассы) запускается первым; параллельно ему в основной сессии пишется design-док-бриф ingest 3.2 — при застревании трейсера на подсрезе 2 ingest стартует без потери времени.
2. Публичная коммуникация трейсера — только после завершения подсреза 3; до того трейсер — внутренний architecture probe.

Следствие решения: LLM-компонент трейсера — заглушка (трейсер идёт до этапа R4); реальный LLM-судья подключается после R4 заменой provider-заглушки, вне среза трейсера.

Rationale: трейсер — единственный артефакт, демонстрирующий незанятую нишу (applicability skill × environment + провенанс + вето у хоста) и принудительный ревизор контрактов 3.0; ingest не доказывает ничего, чего нет у Archcore, и его ценность растёт с числом принявших проектов, которых пока нет. Скелет роадмапа не переупорядочивается — probe есть вставка между R3 и R5.

### С3(б) (принято). Поставляемый контент — RU, с языковым триггером.

Состав решения:
1. Поставка (10 модулей, 3 шаблона, 4 SKILL-тела) — RU; README получает пометку «content is currently in Russian» (W3, часть 6.2).
2. Триггер: EN-перевод поставки — обязательное предусловие первой публичной коммуникации трейсера: пост, Comparison, продвижение, смена GitHub description на трейсер-нишевое.
3. При срабатывании триггера перевод совмещается с 2.5б/2.6 в один проход (перевод правила и есть его переписывание; no-op строки отваливаются в процессе).
4. Двуязычие отклонено: двойное сопровождение при одном мейнтейнере гарантирует дрейф версий — самоопровержение для инструмента, продающего консистентность правил.

### С4 (принято). Модель публикации — continuous release, с триггером перехода.

Состав решения:
1. Пока marketplace-entry указывает на `./plugins/glue` текущей ветки, **merge в main изменения `plugins/glue/**` (с обязательным бампом version) есть публикация новой версии**. Публикация авторизуется **двумя независимыми подтверждениями перед одним физическим merge** (по `operator-gate.md`): буквальное подтверждение публикации версии X.Y.Z, затем — после свежей перепроверки — отдельное «мержь»; строка «merge = публикация версии X.Y.Z» в PR-описании раскрывает эффект, но не заменяет авторизацию. Тег — постфактум-фиксация, не гейт публикации.
2. Триггер: **переход на controlled release** (исполняется пунктом 6.3: стабильный ref/channel/sha в plugin source marketplace-entry, чтобы main перестал быть публикацией) — обязательное предусловие первой публичной коммуникации трейсера, **либо срабатывает раньше — при первом свидетельстве внешнего использования** (issue/PR извне, сообщение об установке, любой сигнал внешней аудитории).
3. До срабатывания триггера controlled-машинерия не строится.

Rationale: на момент решения **известных** внешних пользователей нет (репозиторий публичен и README содержит install-команды, поэтому отсутствие установок не доказуемо — отсюда вторая ветка триггера) — continuous честно отражает фактическую механику (marketplace update тянет текущую ветку, изменённый version — cache key) без новой инфраструктуры; операторский контроль публикации сохраняется, поскольку каждый merge уже проходит операторский PR-гейт. Controlled начинает окупаться ровно с появлением внешних пользователей — то есть с первой публичной коммуникацией, на которую и поставлен триггер.

## Мета-дисциплина задания

**Правило проверки:** любое утверждение о состоянии репо или конкурентов — с командой/URL и датой проверки. Совпадение имён ≠ совпадение содержимого — сверять diff'ом.

**Правило первоисточника решений:** решение существует, когда зафиксировано в адресуемом артефакте репо (задание, decision-карточка, dogfood-отчёт, PR). Переписка — не источник провенанса. Карточка ссылается на артефакт, содержащий **результат** решения, а не намерение его принять.

**Правило носителя:** версия в имени (`_vN.md`); действующая одна; переработка → `_vN+1.md`; дельта-цепочки и ссылки «как в vN» запрещены — всё нормативное живёт inline в действующей версии.
